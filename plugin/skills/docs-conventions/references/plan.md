Purpose: section rules for `specs/<id>/plan.md`. Template: `assets/plan.md`.

Frontmatter: `spec`, the spec id.

Two parts. Every line above Scope is what the owner reads to say OK: Approach, How it works and Contracts. It follows the rule for text the owner reads to decide, in `SKILL.md`. Scope and what follows it is what the build works from. Nothing the owner has to agree to is left only in `reference/`.

Approach: required. What will be built, as a list with one complete fact per line, as many lines as the owner needs to judge, usually 3 to 10. Each line starts with the thing it is about, in bold. A decision is a line here when it does one of three things: it changes what a user sees or can do; it crosses a boundary, which is a contract, a dependency between modules, or data sent to or read from the outside; or it deletes or removes something. Where the route taken is not the obvious one, the reason is in the same line. Where a line rests on something that could not be read from the code or the docs, it ends with **Not checked:** and what was assumed. No list of choices and no options that were not taken: a real choice is asked before the plan is written, and a lasting one gets a decision record. Don't restate the why. A size or value that arrives mid-build goes to `reference/`, not here.

How it works: only when a picture explains the change faster than text. That is the case when three or more parts pass something to each other in an order, a part being a module or a service outside the product: draw it, even when the Approach says the same in words, because a flow is read faster as a picture. Leave the section out for a change inside one module and for two parts that call each other. One mermaid diagram. Pick the kind that fits the case: a numbered sequence, `sequenceDiagram` with `autonumber`, when the order of steps between parts is the point; grouped boxes read from top to bottom, `flowchart TB` with one `subgraph` per owner and numbered steps, when who owns what is the point; another kind when it fits better. Steps are numbered where there is an order. Every arrow has a label in plain words that says what is passed or asked. Boxes are named in product words. About eight boxes at most. Never a picture that only shows which module imports which. A rule such as "A never loads code from B" is a note in the diagram or a line in the Approach, not an arrow.

Contracts: when a contract is new or its shape changes, and it crosses a boundary. Three kinds cross one: what a module offers to another module; what the product exchanges with the outside, such as requests, responses, events, stored data and web addresses; and something shared that other code already uses. A module is what `architecture/boundaries.md` lists, or a top-level source folder when it lists none; a file inside a module is not a module. One small code block per boundary, each under one line of plain words that says what it is and who uses it. Code in the project's language, with the names the code uses. Changed members only: for a type that exists, only the fields that are added or change. A field that could not be read from the code is marked `// not checked`. A page or component that another module mounts is a contract even when it takes no data: one line of code with its name. A contract that only moves to another place, or is removed, is one line in the Approach and no code. Never what only the module being built uses, an unchanged type, a cache key, or a function body.

Scope: required. A tree in a `text` block of the folders or files the change may land in. A shared folder is written once and what is under it is indented. One path per line, never several files on one line. After the path: `+` for new, `~` for changed, `-` for deleted, then a reason of a few words. A folder line covers everything under it, so a module that gets several files is one line. Code, test and config paths only: the docs the flow itself writes, the spec folder, `behavior/`, `architecture/` and `decisions/`, are never listed. This is where spec-build writes without asking and what the review checks the diff against. Not line-level edits. A plan written with flat lines or a Files heading is read the same way.

Architecture to update at ship: optional, when an architecture area changes. Each area file and the plan section or the reference file it comes from. spec-ship updates exactly these. Not the content itself.

Rollout: optional, only when order matters. Migrations, flags, deploy order, backfills. Not standard deploy steps.

Risks: optional. What could break and which claim or test covers it. Not generic risks.

An owner's part that does not fit on about two screens means the spec is too big, or it holds detail the OK does not need, which belongs in `reference/`. A plan written with a Trade-offs heading stays valid.
