Purpose: lasting choices made while specifying and building plan-shows-design, appended as they are made, never edited.

## D1 The design lives in the plan, in a part written for the owner
2026-11-27. The owner's OK has to cover the architecture, and Yousef does not want a big file to read without a real benefit. So the plan opens with what he reads to say OK, the approach, the contracts, the dependencies and the picks, capped at about 40 lines, and what the agent builds from, the Scope, the architecture files to update, rollout and risks, comes after it. A separate design document was not chosen: it would be one more file to read and one more OK. The cap sits on the owner part only, since a Scope with many rows is for the build and the review. A section with nothing to show is left out, as the conventions already require.

## D2 Three parts of the other team's design guide are left out
2026-11-27. The guide Yousef liked also has an observability table, a critical-code section, sequence diagrams and a separate agent that grills the person on the written design and ends in a fixed summary. He kept the contracts as code, the dependency view and the list of picks. The table applies only to services with metrics and would be an empty heading in most plans. The grilling skill that exists takes the useful idea, questioning a written draft, without a second skill. Sequence diagrams and critical code wait until a real plan shows the need. How a question is put stays with the agent; the skill says what must be asked.

## D3 The dependency view is one mermaid flowchart
2026-11-27. Plain arrows in a text block were the other option. Yousef chose mermaid, held to about ten nodes: it renders as a picture on GitHub and in the apps he reads plans in, and its source still reads as arrows where it does not render. One diagram, so the owner's part stays short.

## D4 A contract is what another module or system calls or reads
2026-11-27. Exported types and function signatures, component props, endpoints, events and schema. A module's internal helpers are not contracts and stay out of the plan. The line follows what the owner corrects in practice: the surface other code depends on, which is costly to change once it is built on.

## D5 A fix that changes the design gets a plan
2026-11-27. A fix has no plan, and a refactor is a fix, so a change that moves a contract or a dependency could reach the build with nothing shown. Yousef chose that such a fix gets a plan with the owner's part and waits for the OK. Every other fix stays one pass.

## D6 The build asks before leaving the design, and the ship review checks it
2026-11-27. Without both, the OK would cover a design the code is free to leave. spec-build asks before a contract or a dependency the plan does not show, as it does for a path outside the Scope, and on yes the plan is updated. The answer changes neither `spec.md` nor the Scope, so no task recheck follows. The fresh reviewer reports both directions: in the diff and not in the plan, in the plan and not in the diff.

## D7 An architecture file may come from a plan section
2026-11-27. With the design in the plan, an entry under Architecture to update at ship names a plan section or a reference file. Copying the Contracts into a reference file only to name it would be text nobody reads.

## D8 Two picks of the agent's, shown at the go
2026-11-27. Not asked as questions, listed for Yousef beside the request for the go. A design finding does not stop the ship: the two findings that stop it protect what `behavior/` asserts about the product, and a design drift does not make a claim false. The AGENTS.md block gains no line: a block change makes every project rerun docs-init, and the check runs in spec-ship either way.

## D9 The two guard rails are deferred
2026-11-27. The build stop and the ship check for code that leaves the agreed design were approved on a paper argument: without them the OK covers a design the code is free to leave. No build has ever left an agreed design, because no plan held one. Read literally, the build rule would also have asked about every export in a plan written before this version. Yousef agreed to drop both from this spec. They are lines in `reference/follow-ups.md`, to be specified when real use shows a build leaving the design. D6 and the first pick in D8 no longer apply to this spec.

## D10 A contract is shown when it crosses a boundary
2026-11-27. Yousef saw that a rule listing every exported thing would make the plan huge on a real feature. A contract is shown when it is offered by one module to another, exchanged between the product and the outside, or shared and already used by other code. What only the module being built uses stays out. A module is what `architecture/boundaries.md` lists, or a top-level source folder when it lists none. This narrows D4. In the trial below the two wordings gave the same result, five and six contracts for a feature of about thirty files, so the wording is a clarification and not what keeps the plan short.

## D11 Readable to judge replaces the line limit
2026-11-27. Yousef: the limit is not what matters; the plan needs his attention, so it has to be easy to scan, read and understand. And: the goal is to read and judge, not bullet points for looks, and not cut-down wording or code words that assume the reader already knows. The rules: one complete fact per line; product words, with the code name only where it is needed to find the thing; simple common words; a choice in three lines, the choice, the other way and the reason; one small code block per boundary under a plain label. The cap of about 40 lines in D1 is withdrawn. Two screens stays as a sign that the spec is too big, never as a test. He wants the same rule for every text he has to read to decide, so the claim sits under docs-conventions and the next spec brings its cases for `spec.md` and for questions.

## D12 A diagram only when it helps, of the kind that fits
2026-11-27. The first real plan drew three unlabelled arrows between module names, and Yousef said it told him nothing. He likes diagrams because a picture of the flow makes him understand fast. So a diagram is drawn only when a picture explains the change faster than text, its kind is chosen for the case, steps are numbered where there is an order, every arrow carries a plain label, and boxes are named in product words. Shown two versions of the same flow, a numbered sequence and grouped boxes, he chose the sequence for that case and said the kind must not be a rule. A new or avoided dependency between modules is a choice and is listed as one. This replaces D3 and the Dependencies section.

## D13 The Scope is a tree
2026-11-27. Yousef found the Scope lines of a real plan unreadable: each repeated a long path and packed a list into one sentence. The Scope becomes a tree in a text block: a shared folder written once, one path per line, `+` for new, `~` for changed and `-` for deleted, and a reason of a few words. A folder line still covers everything under it. A plan written with flat lines, or with a Files heading, is read the same way.

## D14 The writer asks why the reader needs this, and the document never says so
2026-11-27. Yousef asks "why am I reading this?" before he reads anything, so the writer asks "why does the reader need this?" before writing it. A line with no answer is cut, or moved to the part the agent builds from. It is a question in the writer's head: I first wrote it into an example plan as two opening lines, and he corrected that the same day.

## D15 The fix rule stays, proven on a real refactor
2026-11-27. In the trial a refactor filed as a fix was handed over with "build this fix". With the rule the agent planned first, showed two contracts and wrote no code. D5 stands.

## D16 The rules name two kinds of diagram as guidance, and prescribe neither
2026-11-27. On a second look Yousef found the grouped boxes as clear as the numbered sequence, and said again that the agent picks by the case. The rules for the plan name both with the case each fits: a numbered sequence when the order of steps between parts is the point, grouped boxes read top to bottom when who owns what is the point. Another kind is allowed when it fits better. No case grades which kind was drawn.

## D17 No list of choices; a guess is marked where it appears
2026-11-27. A second trial ran the three real specs again under D11 to D13, with a section of choices in three lines each. The plans read well and were two to three times longer: 148, 99 and 68 lines above the Scope against 44 to 51. I proposed to keep the list and shorten it by listing only choices the owner "might want the other way". Yousef called that phrasing dangerous, and it was: it lets the agent judge what the owner cares about and stay silent on the rest. He then asked why the section exists at all: once the plan is agreed its choices are no longer relevant, and the Approach already covers them. The section is dropped. The Approach says what will be built, with the reason in the same line where the route is not the obvious one; a real choice is a question before the plan is written, which the grilling rule already requires and the next spec makes reliable; a lasting choice gets a decision record. Only a guess stays visible, something the agent could not read from the code or the docs. It is marked at the place it appears, "Not checked" in the Approach and `// not checked` in a contract, with no section of its own. This replaces the choices part of D11.

## D18 A contract is shown as code only when it is new or its shape changes
2026-11-27. In the second trial the Contracts section of the largest plan was 87 lines. It held cache keys, a helper that only moved to another folder and a web address that was removed. A contract is now shown as code when it is new or its shape changes, and when it crosses a boundary as in D10. A move or a removal is one line in the Approach. Cache keys are how the code works inside and are left out.

## D19 What matters is in the Approach, by three tests the agent can see
2026-11-27. With the list of choices gone, Yousef asked whether to keep it for what the Approach does not hold. A leftover section would hold either something that matters to him, which belongs in the Approach where he reads first, or something that does not, which belongs nowhere in his part. So there is no leftover section. A decision is a line in the Approach when it changes what a user sees or can do, crosses a boundary, or removes something. The agent can check all three without guessing what the owner cares about. The limit of 3 to 8 lines is relaxed to as many lines as he needs to judge, so the agent is not pushed to leave one out. A decision that meets none of the three and was not asked stays out of his sight; those are cheap to change.

## D20 The go, and three fixes from the third trial
2026-11-27. A third trial planned the three real specs again under D17 to D19: 86, 63 and 62 lines above the Scope against 148, 99 and 68. Yousef read the middle one and gave the go. Three things the trial showed went into the build. The template no longer carries a comment that marks where the owner stops reading: every agent deleted it, because a finished file holds no comments, and "every line above Scope" says the same. A page or component that another module mounts is a contract even when it takes no data, shown as one line of code; one agent had to ask. Two agents wrote a decision record before the owner's OK, and the pack does not say whether that is allowed; that is an open point for `2026-11-27-ask-before-assuming`, not for this spec.

## D21 The design case gets a sign-in package the agent cannot read
2026-11-27. "Not checked" needs something that cannot be read. The fixture of shows-the-design now has a session module that re-exports from a package that is not installed, and the prompt says the wishlist asks it who is signed in. That gives the case one real guess to mark, and three parts that work together, the sign-in service, the wishlist and the catalogue, so a diagram is expected there. The other cases keep the plain webshop.

## D22 The template shows where the mark goes
2026-11-27. One by-hand run wrote the Scope tree with the mark before the path, `+ wishlist.ts`, where the rules say after. The template's comment listed the marks without their place. It now says "after the path" and carries one slot line that shows it.

## D23 The ship case is a guard, not a fix
2026-11-27. updates-architecture-from-a-plan-section passed on the 0.5.0 skills: given `contracts.md, from Contracts`, the agent wrote `architecture/contracts.md` from the plan section although the step said "from the named reference file". The step's wording now says "the plan section or the reference file", and the case stays to keep it that way. The case of the planned fix no longer looks for a Dependencies heading: the dependency that changes is a line in the Approach, and its grader reads that line.

## D24 When to draw is a test the agent can see
2026-11-27. The by-hand runs on Sonnet drew a diagram for shows-the-design both times. The runner on the default model drew one in one run of seven: the rule ended with "leave the section out when a sentence says it as well", and that model judged the Approach said it as well. Yousef reads a flow faster as a picture and approved plans that had one, so the rule's result must not depend on the model's taste. The rule now names what the agent can see, as D19 does for the Approach: three or more parts, a part being a module or a service outside the product, pass something to each other in an order. Then the diagram is drawn even when the Approach says the same in words. A change inside one module and two parts that call each other get none. The claim in `spec.md` is unchanged. In the same run one plan wrote its Approach without bold topics; the template's comment now says "in bold", as the rules already did. After the change shows-the-design passed four of four runs in the runner and draws-no-diagram-inside-one-module still drew nothing.

## D25 Diagrams get three small rules, not a skill of their own
2026-11-27. Yousef found two public Mermaid skills and wanted the pack to draw as cleanly as their examples, with no fixed kind. A draft practice was tried on a real project: three requests, each drawn with and without it. The sequence came out better. The other two did not satisfy him, in the kind chosen and in the look, and redrawing them by hand showed what the public skills teach and the draft lacked: very short labels, shapes that mean something, and a split drawn in the diagram. A practice that teaches that for every kind needs a page per kind. He said the plan's diagrams as they stood were not bad, that he only wanted an improvement, and that it must not cost context. So the practice is parked as a follow-up, and the plan's diagram rule gets what the trial showed at about 70 words: two more kinds named, a label of eight words at most, and a split that matters drawn as a split. No claim changes.
